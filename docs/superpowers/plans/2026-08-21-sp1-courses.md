# Sous-projet 1 — Liste de courses : plan d'implémentation

> **Pour l'exécutant** : ce plan est exécuté dans la session qui l'a écrit, avec le
> contexte des contrats d'API déjà lus. Chaque tâche suit le cycle test rouge →
> implémentation → test vert → vérification. Les étapes portent une case à cocher.

**Objectif** : rendre la liste de courses utilisable dans l'application — ajouter un
article, s'en attribuer un, déclarer l'achat, voir l'avancement — sur l'API existante.

**Architecture** : un client d'API par domaine, comme `EvenementsApi` ; un provider
Riverpod par lecture ; un écran branché dans l'onglet déjà réservé de
`CoquilleEvenement`. Aucune modification côté API n'est attendue.

**Pile** : Flutter 3.38, Riverpod 3, `go_router`, Dio. Tests `flutter_test`.

**Spécification** : `docs/roadmap.md` lot 1.5 (`EF-CRS-01` à `EF-CRS-10`, `RG-CRS-01`
à `RG-CRS-03`) et `docs/cahier-des-charges.md` §8.2.

**Cadrage** : `docs/superpowers/plans/2026-08-21-achevement-v1-cadrage.md`.

## Contraintes globales

- Français dans l'interface, anglais dans le code et les identifiants de base.
- L'identité d'un participant est sa ligne `event_members`, jamais `user_id` : un invité
  sans compte doit pouvoir s'attribuer un article et déclarer un achat.
- Montants : jamais de `double` porteur de sens métier côté API. Côté Dart, les montants
  arrivent en `num` depuis JSON et sont convertis en `double` pour l'affichage seul, via
  `PpMoney` — aucun calcul de répartition n'est fait dans l'application, le serveur est
  seul juge (`RG-RMB-02`).
- Toute création porte un en-tête `Idempotency-Key` : `POST /shopping` et
  `POST /shopping/{id}/purchase` l'exigent, `claim` et `release` non.
- `flutter analyze` sans avertissement et `flutter test` vert avant chaque commit.

## Contrat d'API existant, vérifié le 21/08/2026

Préfixe : `/v1/events/{eventId}/shopping`.

| Méthode | Chemin | Corps | Réponse | Idempotence |
|---|---|---|---|---|
| GET | `/` | — | `ShoppingList` | — |
| POST | `/` | `ShoppingItemBody` | `ShoppingItemView` | obligatoire |
| PATCH | `/{itemId}` | `ShoppingItemBody` | `ShoppingItemView` | non |
| DELETE | `/{itemId}` | — | 204 | non |
| POST | `/{itemId}/claim` | — | `ShoppingItemView` | non, idempotent par nature |
| DELETE | `/{itemId}/claim` | — | `ShoppingItemView` | non |
| POST | `/{itemId}/purchase` | `PurchaseBody` | `ShoppingItemView` | obligatoire |

```
ShoppingList     { progress: ShoppingProgress, items: ShoppingItemView[] }
ShoppingProgress { total: int, claimed: int, purchased: int }
ShoppingItemView { id, name, quantity, unit?, category,
                   assignedMemberId?, assignedDisplayName?, assignedToMe,
                   isPurchased, purchasedQuantity?, remainingQuantity,
                   estimatedPrice?, actualPrice?, note? }
ShoppingItemBody { name, quantity?, unit?, category?, estimatedPrice?, note? }
PurchaseBody     { purchasedQuantity?, actualPrice? }
```

`category` est sérialisée en chaîne parmi `Drinks`, `Food`, `Supplies`, `Other`
(`EF-CRS-02`). Libellés français à l'affichage : boissons, nourriture, matériel, autres.

Codes d'erreur métier à traiter à l'écran :
- `shopping.already_claimed` — un autre participant a pris l'article entre-temps
  (`RG-CRS-01`). L'écran recharge et le dit, il ne réessaie pas.
- `shopping.item_not_found`, `event.not_found` — 404, message neutre (`RG-SEC-02`).
- `shopping.expense_attached` — suppression refusée, une dépense est rattachée
  (`EF-CRS-08`).
